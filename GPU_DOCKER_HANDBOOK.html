GPU Docker Handbook

What is inside a GPU image, where each CUDA library comes from, when pip has to compile something and what it needs, and which system libraries ML packages expect. Sizes marked “measured” come from real project images; other sizes are rough and change between versions.

How the GPU gets into a container

Three layers. Only the bottom one is in your image. Mixing them up causes most GPU problems.

Host driver
Installed on the machine, never in the image. Windows + Docker Desktop: the normal Windows NVIDIA driver (Docker uses it through WSL2). Linux: the NVIDIA driver + the NVIDIA Container Toolkit. nvidia-smi on the host shows the highest CUDA version this driver supports.
Injected at run
docker run --gpus all mounts the driver's user-space parts into the container: libcuda.so, libnvidia-ml.so (NVML), nvidia-smi, and with the video capability libnvcuvid.so / libnvidia-encode.so (hardware video decode/encode).
In the image
The CUDA toolkit libraries your code links against: libcudart, cuBLAS, cuDNN, cuFFT … They come either from an nvidia/cuda base image or from pip wheels (nvidia-*-cu12, pulled in by torch / onnxruntime-gpu). Never both, if you can avoid it: that is the same 3–5 GB twice.

The four things that must match

A GPU image works only when all four line up. Check them in this order.

1. Host driver ≥ the CUDA version in the image

Quick check: the “CUDA Version” in the top right of nvidia-smi (on the host) is the newest CUDA the driver can run. The image's CUDA must not be newer.

RTX 50 series. Everything that runs GPU code must be built with CUDA 12.8 or newer. PyTorch: the cu128 (or newer) wheels, torch 2.7+. Check what a torch build supports with torch.cuda.get_arch_list().

3. Framework build ↔ CUDA / cuDNN major version

cuDNN 8 and cuDNN 9 are not interchangeable, nor are CUDA 11 and 12 libraries. Details per framework are in Frameworks and CUDA.

Pip CUDA libraries live in site-packages/nvidia/<name>/lib. torch finds its own; onnxruntime needs them on LD_LIBRARY_PATH (or onnxruntime.preload_dlls() in 1.21+). Without that: “Failed to load library libonnxruntime_providers_cuda.so” and a silent fall back to the CPU.
# python:3.12-slim image, CUDA from pip wheels: let onnxruntime find them
ENV LD_LIBRARY_PATH=/usr/local/lib/python3.12/site-packages/nvidia/cudnn/lib:/usr/local/lib/python3.12/site-packages/nvidia/cublas/lib:/usr/local/lib/python3.12/site-packages/nvidia/cuda_runtime/lib:/usr/local/lib/python3.12/site-packages/nvidia/cuda_nvrtc/lib:/usr/local/lib/python3.12/site-packages/nvidia/cufft/lib:/usr/local/lib/python3.12/site-packages/nvidia/curand/lib

Compiling: when pip needs a compiler, and with what

pip compiles when there is no prebuilt Linux wheel for that version and Python: the package publishes only source, the pin is older than the Python version, or it is Windows-only. Signs in the build log: Building wheel for X (pyproject.toml), then gcc: not found, pg_config executable not found, Python.h: No such file.

Find these before building: xray_naive.py in xray-tools checks every requirement against Linux for a given Python, or by hand for one package: pip download --only-binary=:all: --platform manylinux2014_x86_64 --python-version 3.12 --no-deps -d tmp PACKAGE==VER (fails = no wheel).

Three patterns that keep compilers out of the final image

Compiler for one step

Install, pip, remove in the same RUN: the compiler never lands in a layer.

Build stage

Build wheels in python:3.X (has gcc), install them in python:3.X-slim.

Prebuilt alternative

Swap to a package that ships wheels: psycopg2-binary, opencv-python-headless, PyMySQL, a newer pin.

# pattern 1 - gcc only during pip (python:3.X-slim)
RUN apt-get update && apt-get install -y --no-install-recommends gcc libc6-dev \
 && pip install --no-cache-dir -r requirements.txt \
 && apt-get purge -y --auto-remove gcc libc6-dev && rm -rf /var/lib/apt/lists/*
# pattern 2 - build stage + slim final image
FROM python:3.12 AS build
COPY requirements.txt .
RUN pip wheel --no-cache-dir -w /wheels -r requirements.txt

FROM python:3.12-slim
COPY --from=build /wheels /wheels
RUN pip install --no-cache-dir --no-index /wheels/* && rm -rf /wheels

Never

  • install the NVIDIA driver inside an image;
  • ship a devel image to production;
  • mix cuDNN 8 and 9, or CUDA 11 and 12 libraries, in one process;
  • install onnxruntime and onnxruntime-gpu together;
  • pin torch==…+cu126 for RTX 50 GPUs.

Check it in a container

From Windows CMD. IMAGE is your image name.

docker run --rm --gpus all --entrypoint "" IMAGE nvidia-smi
docker run --rm --gpus all --entrypoint "" IMAGE python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available(), torch.cuda.get_arch_list())"
docker run --rm --gpus all --entrypoint "" IMAGE python -c "import torch; print(torch.backends.cudnn.version())"
docker run --rm --gpus all --entrypoint "" IMAGE python -c "import onnxruntime as o; print(o.__version__, o.get_available_providers())"

Which CUDA library is missing for onnxruntime (inside the container, docker run --rm -it --gpus all --entrypoint bash IMAGE):

ldd $(python -c "import onnxruntime,os;print(os.path.dirname(onnxruntime.__file__))")/capi/libonnxruntime_providers_cuda.so | grep "not found"
# only libcuda.so.1 may be "not found" when the container was started WITHOUT --gpus

Which libraries a running process really loaded, and which GPU memory each process holds:

awk '{print $6}' /proc/PID/maps | grep '\.so' | sort -u
nvidia-smi --query-compute-apps=pid,used_memory --format=csv
pip list | grep -i -E "nvidia|torch|onnx|opencv"

Does a package have a Linux wheel for Python 3.12 (no download of the package itself, run anywhere pip runs):

pip install --dry-run --no-deps --ignore-installed --only-binary=:all: --target tmp --python-version 3.12 --implementation cp --abi cp312 --abi abi3 --abi none --platform manylinux2014_x86_64 --platform manylinux_2_28_x86_64 PACKAGE==VERSION
Driver minimums, architectures and image contents follow NVIDIA's published compatibility tables; sizes marked rough vary by version. Measured sizes come from real project builds. Re-check versions against the vendor pages before pinning production images.
