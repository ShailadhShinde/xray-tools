Office rules

Read these once before step 0. They apply to every step.

No code changes

Everything here is Dockerfiles, run files and compose. What only the code can fix goes to code-changes.txt and the code owner list.

A run is a second worker

Steps 5, 6, 8 and 10 start the worker against the real cameras and database. Agree with the team first, and stop the production worker or give the test its own camera. Recognised faces go to a test folder, never the dashboard's.

No secrets in chats or files

Replace the database password, camera addresses with user:password@, the licence MAC and people's names with *** before you paste anything. The password sits in constants.py: never copy it into a .bat file, an .env on GitHub, or a chat.

Personal data

Photos of recognised people land in runs\worker\files*, with their names as folder names. The names also appear as file paths in X-Ray's reports (verify.txt, the .json files). Don't share the folders, and replace names with *** before you paste a report. Delete the photos when the tests are done (step 10).

Office files stay off GitHub

runs\worker, logs and reports go only into the chat, redacted. This page holds no password, address or name: what you type in the settings stays in your browser.

The map: how the worker runs, and what Docker must give it

From your description of the system and what the runs showed. Keep it in mind for every step.

In the dashboard (the domain_url), someone adds cameras and picks the solutions for each one (face search, in/out count) with their parameters (AOI ...). All of it is stored in the database.

main.py starts: the licence check (license_check.py) reads the network card's MAC, then the worker reads its camera and solution list from the database.

In a container the MAC is random unless you give it one. your run The first run on 9 Oct stopped by itself after 10 s, before any camera started: the licence check, or no camera set for this machine.

It starts its own processes (spawn): Produce_Frames processes read the RTSP streams into shared memory, and other processes run the models on the GPU (onnxruntime with CUDA, torch).

your run 4 cameras: 13 processes, 8.3 CPU cores busy, the GPU's memory 11.9 of 12.3 GB.

Results go to the database. Photos of recognised faces go into the dashboard's images folder (a Linux path written in constants.py). Logs go to logs\... next to the code.

The driver comes from the PC

--gpus all mounts libcuda.so and nvidia-smi into the container. Every other CUDA library must be inside the image.

torch brings its own CUDA

torch's wheels pull in NVIDIA's CUDA libraries as pip packages (nvidia-cudnn-cu12, nvidia-cublas-cu12 ...). A CUDA base image under it is a second copy. That copy is what the slim image dropped.

Libraries are found by name

onnxruntime opens libcudnn.so.9 and the others by name. Linux finds them through LD_LIBRARY_PATH or the folders registered with ldconfig. The slim Dockerfile registers the wheels' folders.

The naive image

2 min · keep the one you have

You have it: worker-naive, built on 9 Oct from Dockerfile.naive in the project folder. It ran the worker on the GPU, and verify compares every new image with it. Keep it as it is.

One typo in that Dockerfile: X-Ray reported env vars set for the container but never read by the code: PUTHONUNBUFFERED. The name is PYTHONUNBUFFERED=1. With the right name the worker's prints reach the log at once. In your 9 Oct log they came only at the very end, after the KeyboardInterrupt lines, when each stopped process emptied its buffer. Fix the spelling whenever you rebuild (runs\worker\build-naive.bat after step 3; the downloads are cached, so it is quick).

It checks every requirement for Linux and writes a Dockerfile.naive that builds, each line with its reason (naive-check.txt says why). Two things it has to handle here, both from your earlier builds:

  • netifaces and cython-bbox have no ready-made Linux wheel: pip compiles them, so the build needs gcc for that step.
  • torch==2.8.0+cu126 is only on PyTorch's own index (download.pytorch.org/whl/cu126), not on PyPI.

New in 0.4.5: the Python version comes from the project's own venv (venv\pyvenv.cfg) when there is one; line 2 of naive-check.txt says where it came from. psycopg2 no longer shows as "no file for Linux ... at all": pip could not prepare its source on your PC because PostgreSQL's pg_config is not there. That is a check on the PC only. It now shows as COMPILED, and the Dockerfile installs libpq-dev for the build (or use psycopg2-binary, as the slim plan does).

If it warns that your pip checks Requires-Python against this PC's Python: python -m pip install -U pip, then run it again.

It looks at the image only: it starts no worker and touches no camera or database. It lists the biggest packages, what each compiled file needs, every CUDA library and where it comes from, imports every package, and tests the GPU with each framework.

Check in look-naive.txt

  • GPU TEST: torch says GPU: True with your card; onnxruntime lists CUDAExecutionProvider (built in; step 5 shows it really runs on the GPU).
  • DOES EVERY PACKAGE IMPORT: FAILED: none.

What compose.yml holds

  • restart: unless-stopped: the worker runs until you stop it, and comes back after a reboot. Right for a camera worker.
  • mac_address from .env; the GPU; the photos folder mounted at the path the code writes to (the one in your settings); LOGS_DIR at /app/logs.
  • shm_size: 4× what the step 5 run measured, at least 256m. Step 5 ran one camera; on 9 Oct four cameras used 84 MB. For more cameras, raise it: df -h /dev/shm inside the running worker (step 6) shows the use.
  • .env holds everything that differs per machine. Never put it on GitHub.

Check

  • docker compose ps shows it running; docker compose logs shows the cameras starting, not a licence message.
  • New recognitions appear in the dashboard, and their photos in the folder of RECOGNIZED_PEOPLE_DIR.
  • Permission denied writing the photos or logs on a Linux machine: the slim image runs as uid 1000. sudo chown -R 1000 <folder> for both folders.

When something breaks

You seeWhat it means, what to do
The run ends after about 10 s, 1 process, "no GPU use seen"The worker stopped itself before starting cameras: the licence (missing or wrong MAC) or no camera and solution for this machine. End of step2.log and logs\main_logger; then the MAC in the settings and step 3, or the dashboard.
A licence message in step2.logThe MAC in the run file is not the licensed one. Run xray_runfile.py again with the right --mac (step 3), or correct --mac-address in the run file.
Database: timeout, could not connect to serverTest-NetConnection (step 0) from this PC. False: the PC is not on the database's network (VPN, another site).
A camera does not openCan this PC reach it? Open the camera's address in VLC on the same PC. Docker reaches what the PC reaches.
CUDA out of memory, Failed to allocate memoryThe GPU is full: every solution process needs its own GPU memory. Fewer cameras or solutions per worker, or a card with more memory. Step 10 shows where the limit is.
Bus error, or an error about /dev/shm / SharedMemoryShared memory too small for the frames: raise --shm-size in the run file, or shm_size in compose.yml.
Could not load the Qt platform plugin "xcb", exit code 134 or 139 (run-naive, compose)A window, with no screen: NO_WINDOWS=1 in .env (compose) - run-naive sets it itself. To see the windows: run-window.bat.
Permission denied on /app/logs or the photos folder (slim image)The slim image runs as uid 1000. On a Linux machine: sudo chown -R 1000 on the mounted folders.
