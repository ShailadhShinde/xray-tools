The flow: two images, one proof

The naive image is built the usual way and is the reference. The slim image is built from what the program really used, and verify proves it does the same.

Read the code (step 1) and the requirements (step 2): what the program needs, written as a Dockerfile.naive that builds.

Run the program in that image, alone (step 4) and with X-Ray watching (steps 6, 7): what it really imports, opens, loads, connects to, writes; RAM, CPU, GPU.

Plan the slim image from that evidence (step 8): only the packages, libraries and files that were used, each line with its reason in plan.json.

Prove it: the same run on the slim image, compared fact by fact (step 9: VERDICT: PASS), and both images side by side (step 10).

Ship it with a compose file and one .env per machine (step 13).

Linux, always

Docker Desktop on Windows runs Linux containers; the same image runs on a Linux server. What can differ is the CPU: x86_64 (Intel, AMD) or ARM (Jetson, Raspberry Pi). Step 2 checks the requirements for the one you name.

The driver comes from the PC

--gpus all mounts the NVIDIA driver into the container. Every other GPU library must be inside the image: from an nvidia/cuda base or from pip wheels (torch brings its own).

Evidence before removal

Something leaves the image only when no code that ran used it and nothing needed depends on it. Whatever the code can reach stays, even if the test run did not touch it.

Requirements and the naive Dockerfile

2–5 min · pip only reads the package index (GUIDE 2.4, 3b)

CMD · tools folder
python xray_naive.py --project "%P%" --requirements «R» --entry «E» --name «N» --static runs\«N»\«N».json «NG»
notepad runs\«N»\naive\naive-check.txt
Line 2 of naive-check.txt: what it checked for
for: Linux x86_64, Python 3.10 (from venv/pyvenv.cfg (the virtual environment in the project)), GPU image (base ...)

Which Python, which Linux

  • Python comes from the project itself: its venv (venv\pyvenv.cfg), .python-version, pyproject.toml, its own Dockerfile ... Line 2 says where. Nothing found: 3.12. Yours wins: --python 3.10.
  • Linux is always the image's OS. The CPU decides the files: x86_64 by default, --arch aarch64 for ARM.
  • OTHER PYTHON VERSIONS (near the end): for a pin with no Linux wheel, the Pythons that have one. The project's real Python is usually among them.

What you can decide

  • --copy NAME / --mount NAME: a file the code reads from your PC (env var NAME). Copy = into the image at build time: it runs anywhere on its own, the image is bigger, a new file means a rebuild. Mount = attached at run time with -v: the image stays small, the file can change, every machine must have it. Default: up to 500 MB copied.
  • --keep PACKAGE: only when two packages install the SAME files (opencv-python + opencv-python-headless both write cv2/). Both in one image = whichever installs last wins. Keep opencv-python if the program opens windows; -headless is smaller and has none.
StatusMeaningDone for you
OKa ready-made Linux wheel—
COMPILEDonly the source: pip compiles it in the build. Also when pip could not even prepare it on your PC (psycopg2 asks for PostgreSQL's pg_config): that part runs again inside the imagecompiler + -dev library for that one RUN (psycopg2: libpq-dev; or use psycopg2-binary)
MISSINGthat version has no file for Linux and this Pythonthe nearest version that has one, listed under HANDLED; the OTHER PYTHON VERSIONS list says which Python it was made for

second steppins pip will not install together in one goinstalled after the others, exactly as pinned

Look inside the image

5 min · the program does not start (GUIDE 10a)

CMD · tools folder
docker run --rm «GPU»-v "«X»:/x:ro" --entrypoint "" «N»-naive python /x/xray_look.py --image > runs\«N»\look-naive.txt
notepad runs\«N»\look-naive.txt

Check

  • MISSING for an import: none, and DOES EVERY PACKAGE IMPORT: FAILED: none.
  • GPU TEST: torch GPU: True with your card; onnxruntime lists CUDAExecutionProvider.
  • missing only for parts loaded on demand: plugins the program may never load. One line names the Qt window plugin with the apt packages a real window needs.

By hand

  • Under every section a by hand: line gives the same check as a standard command. The commands ask Python where its packages are, so they fit any image: system Python or a venv.
  • A library missing that X-Ray has no package name for: apt-file search NAME (the line says how).
6

Watch it run

RUN_SECONDS (180 s) · your test, with X-Ray (GUIDE 4)

CMD · tools folder
runs\«N»\run-step2.bat

Read step2-needs.txt

  • WHAT THE RUN USED, at the end: RAM (sum of the processes), CPU cores busy, which GPU provider ran, the whole card's GPU memory.
  • The program's own output: runs\NAME\step2.log. KeyboardInterrupt at the end = X-Ray stopping it at RUN_SECONDS.
  • What its windows showed: runs\NAME\trace\gui\, one picture per window every 5 s.

Why the run matters

  • Code reading cannot tell which if runs, which of two packages loads, whether the GPU is really used. The run records it.
  • Make the test real: the inputs and settings production uses. What the run never touches stays in the image only because the code can reach it.

  • VERDICT: PASS and problems (0); with a GPU, it checks the GPU is still in use.

Videos: can the image read them?

programs that read video files

CMD · tools folder
runs\«N»\videos.bat "D:\your videos"

What it does

  • Opens every video with the OpenCV inside the image and reads frames. Any format, because it asks the real library.
  • Converts the unreadable ones (AV1, for example) to H.264 into h264\, checks the copies, prints the run.env line for each.
  • On the GPU when it can: GPU=1 at the top (default). NVIDIA's encoder is tested first; no GPU, or a file it refuses: the CPU. Each line ends with GPU) or CPU).

Check

  • The first convert line says which encoder, and why not the GPU when it is the CPU.
  • The image xray-ffmpeg:2 (about 1 GB) is built the first time only.

Production: compose

no X-Ray · one .env per machine

CMD
cd /d "«X»\runs\«N»\plan"
copy .env.example .env
notepad .env
docker compose build
docker compose up -d
docker compose logs -f

What compose.yml holds

  • The slim image, restart: unless-stopped, the GPU, shm_size (4× what the run measured, at least 256m), the MAC when a licence checks it.
  • Folders: each written path and log folder, mounted from a folder named in .env.
  • OpenCV windows without a switch of their own: NO_WINDOWS=1 in .env and the no_windows folder mounted.
  • The project already has a compose file: the plan writes compose.xray.yml to put on top of it instead.

Check

  • docker compose ps: running; the logs show the work starting.
  • Permission denied on a mounted folder (Linux machine): sudo chown -R 1000 on it; the image runs as uid 1000.
  • .env holds passwords: never in git, never in a chat.

Stop: docker compose down. logs -f: Ctrl+C stops the following, not the program.

If no window opens

  • Could not load the Qt platform plugin "xcb" even though it was found with a screen: the image lacks the window plugin's libraries. WINDOW_APT at the top of run-window adds them in a test image; the names are in step 5's the Qt window plugin line.
  • opencv-python-headless has no window code: no screen helps.

Tested

  • A real OpenCV window from a container on an X display, and NO_WINDOWS on and off in run-naive and compose.
  • Not tested: WSLg itself (no Windows machine here). If run-window shows nothing, send its output.

When something breaks

You seeMeaning, what to do
Build: gcc / pg_config / Python.h not founda package is compiled and its tools are missing: run step 2 again (it adds them), or use the binary package it names.
Build: No matching distribution foundthat version has no file for Linux and this Python: naive-check.txt's OTHER PYTHON VERSIONS says which Python it was made for.
Build: ResolutionImpossiblepins pip refuses together: Dockerfile.naive installs them in a second step; run step 2 again on the current file.
Could not load the Qt platform plugin "xcb", exit 134 / 139a window, no screen: NO_WINDOWS=1 (OpenCV) or the program's own switch; to see it: run-window.
No module named ..., cannot open shared object filestep 5: xray_look.py --image imports every package and names what is missing.
onnxruntime runs on the CPU in the imageits CUDA libraries are not found: step 5's CUDA section, and the folders registered in /etc/ld.so.conf.d.
CUDA out of memorythe GPU is full: less load per container, or a card with more memory (step 12 measures).
Bus error, errors about /dev/shmshared memory too small: --shm-size / shm_size.
A video opens but gives no framea format the image's OpenCV cannot decode (AV1): step 11.
unsatisfied condition: cuda>=12.8the NVIDIA driver is older than the image's CUDA needs: update it.
no space left on devicedocker system df, then docker builder prune and docker rmi for old images.
'for' is not recognized, ls fails in CMDa line for INSIDE the container: first docker exec -it NAME bash.
A Traceback in an xray_*.py filean X-Ray bug: send the traceback.
