The driver comes from your PC

It is the only GPU part that does. --gpus all mounts libcuda.so, libnvidia-ml.so and nvidia-smi into the container. Everything else must be in the image.

Wheels bring most of their libraries

opencv-python carries its own FFmpeg and Qt. Only a few libraries are expected from the system. Those, and only those, go into the apt line.

Libraries are found by name

Linux looks in its standard folders plus LD_LIBRARY_PATH. A library outside those folders is "not found", even if it is in the image.

Why

  • pip update: when the Python on your PC is older than 3.12, pip 24.1 and older check package versions against your PC's Python instead of the image's 3.12, and step 2 shows wrong versions. The tool warns about it; updating pip takes a few seconds and avoids it.
  • nvidia-smi in a container proves three things at once: Docker runs, the GPU reaches containers, and your driver is new enough for CUDA 12.8 images.
  • That nvidia-smi is not in the image. --gpus all mounts it in from your Windows driver. You will meet this again in step 5.
  • Clean start: results from last time must not mix with today's. "No such image" is fine. Keep any nvidia/cuda image you already have: Docker reuses it and does not download 3 GB again.

Check

  • The nvidia-smi table shows your card. Top right, CUDA Version is 12.8 or higher.
  • unsatisfied condition: cuda>=12.8: update the NVIDIA driver (570 or newer).
  • could not select device driver: Docker Desktop cannot see the GPU. Restart Docker Desktop, then update the driver.

Read the code

5 min · CMD · nothing runs, nothing changes

CMD · tools folder
cd /d "«X»"
set "P=«P»"
dir "%P%\live_video.py" "%P%\requirements.docker.txt"
python xray_static.py --root "%P%" --entry live_video.py --requirements requirements.docker.txt --out runs\zip\zip.json
python xray_needs.py runs\zip\zip.json > runs\zip\step1-needs.txt
notepad runs\zip\step1-needs.txt

Requirements file: the commands use requirements.docker.txt, the file you made last time. If it is not in ZIP-main, put your own requirements file name in --requirements here and in step 2. A new CMD window later needs the cd /d and set "P=..." lines again.

The parts of step1-needs.txt (your code fills them)
live_video.py
├─ ...     one branch per kind: screen / windows, model files, data files read, files written,
│          environment variables, Python packages, System (GPU)
TO RUN IT IN A CONTAINER, YOU PROVIDE
  ...      one line per env var, model, data file, output, screen, GPU
CODE CHANGES NEEDED
  ...
NOT USED BY THIS ENTRY POINT (...): ...

What this step decides

  • GPU. If the System branch lists CUDAExecutionProvider, the code asks onnxruntime for the GPU. Step 2 reads that from this file and builds a GPU image.
  • Mounts. Files the code reads from your PC (C:\, D:\) are not copied into the image; their folders get mounted (step 3).
  • Window. If the report lists cv2.imshow: a container has no screen. During the runs X-Ray switches windows off and saves a frame every 5 s instead.
  • Packages. A package listed here but missing from your requirements file: step 6 shows whether the program really loads it.
  • NOT USED: files the program never touches. They stay out of the slim image.

Check

  • CODE CHANGES says none. If it lists something (a hardcoded path, a password), sort that out first.
  • Every file you know is important appears in the tree or is read through an env var.

Dockerfile.naive, section by section

1Base image

Dockerfile.naive
FROM nvidia/cuda:12.8.1-cudnn-runtime-ubuntu24.04
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 \
    DEBIAN_FRONTEND=noninteractive
12.8.1 CUDAcudnn cuDNN 9runtime libraries onlyubuntu24.04 Python 3.12
  • onnxruntime-gpu holds onnxruntime's own GPU code, but not NVIDIA's CUDA libraries. When you ask for the GPU, it opens libcudart, libcublas, libcufft, libcurand, libnvrtc and libcudnn by name. No package in the requirements brings them, so the base image has to.
  • 12.8.1: runs on every current RTX card, RTX 50xx included. Needs driver 570+ (step 0 checked that).
  • cudnn: cuDNN 9 is included; onnxruntime needs libcudnn.so.9.
  • runtime: libraries only. -devel adds the compiler nvcc and headers, about 5 GB more, needed only to compile CUDA code. -base has only libcudart, too little.
  • ubuntu24.04: its Python is 3.12, the version the check ran for.
  • ENV: prints reach the log at once; no .pyc files; apt never stops to ask a question.

2System libraries (apt)

Dockerfile.naive
RUN apt-get update && apt-get install -y --no-install-recommends \
        python3 python3-venv libgl1 libglib2.0-0t64 libx11-6 libxcb1 \
 && rm -rf /var/lib/apt/lists/*
RUN python3 -m venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
  • python3, python3-venv: the CUDA image has no Python. Ubuntu's own python3 has no pip and refuses pip installs into the system Python. A venv brings its own pip; first on PATH, python and pip mean the venv everywhere.
  • libgl1, libglib2.0-0t64, libx11-6, libxcb1: cv2 was built against these and Linux loads them at import cv2. Without libgl1: ImportError: libGL.so.1 (you will cause this on purpose in step 5). t64 is glib's name on Ubuntu 24.04.
  • Cost practice: 254 MB for 53 packages. 137 MB is LLVM, pulled by libgl1 → libglx0 → libglx-mesa0 → mesa-libgallium → libllvm20 (Mesa's software OpenGL).
  • --no-install-recommends: only real dependencies. rm -rf .../lists: the package index is not needed after installing.

3aBig framework first

Dockerfile.naive
RUN pip install --no-cache-dir \
        'onnxruntime-gpu==1.22.0'
  • One layer for the biggest package: 619 MB with its dependencies (numpy, sympy, protobuf). Docker keeps every layer; when a line below changes, this one is reused instead of downloaded again.
  • --no-cache-dir: pip's download cache would otherwise stay in the image.

3bThe other packages

Dockerfile.naive
#   nothing to compile: every package has a prebuilt wheel
RUN pip install --no-cache-dir \
        'numpy' 'opencv-python' 'nvidia-ml-py'
  • All of them have prebuilt Linux wheels, so no compiler is installed (gcc would add about 200 MB).
  • nvidia-ml-py is pure Python. It calls libnvidia-ml.so, which comes with the driver.

4LD_LIBRARY_PATH: nothing to add

  • The base image already sets LD_LIBRARY_PATH=/usr/local/cuda/lib64 and keeps cuDNN in /usr/lib/x86_64-linux-gnu, a folder Linux always searches. Step 10 is the case where this line is needed.

5The code

Dockerfile.naive
COPY . .
CMD ["python", "live_video.py"]
  • Everything in ZIP-main, on purpose: the naive image only has to work. X-Ray then finds out which files are really used, and the slim image copies only those.
  • Dockerfile.naive.dockerignore keeps .git, venvs and caches out even here.
CMD · copy the 3 files into ZIP-main
copy /y runs\zip\naive\Dockerfile.naive "%P%\"
copy /y runs\zip\naive\Dockerfile.naive.dockerignore "%P%\"
copy /y runs\zip\naive\requirements.docker.txt "%P%\"

The tool writes into runs\ and never overwrites your project's files, so you copy them. Docker reads Dockerfile.naive.dockerignore automatically because it sits next to Dockerfile.naive with the same name.

Write the run files

2 min · CMD

CMD · tools folder
python xray_runfile.py --static runs\zip\zip.json --project "%P%" --name zip
notepad runs\zip\run.env
What it prints (names and folders come from your code)
  image zip-naive; entry live_video.py; GPU yes/no; window yes/no; ports ...
  mount <a folder on your PC> -> /xin/<name>     one per file the code reads from your PC
  env   <NAME>=/xin/<name>/<file>              that file, inside the container
  env   <NAME>=/xout/<file>                      an output file, kept in runs\zip\out
  env   <NAME>=cpu   (CPU run only)               an env var whose default is cuda or gpu
  code changes suggested: 0

Why

  • Files the code reads from your PC stay there. -v mounts their folders into the container, read-only. The image stays small and works with any model or video.
  • Inside the container the paths are different, so the env vars point at the container paths: /xin for inputs, /xout for outputs (kept in runs\zip\out).
  • run.env holds every env var once; all run files read it.

Why it is smaller, and the catch

  • The CUDA part shrinks from 4.38 GB to 2.58 GB: cuSOLVER, cuSPARSE, NCCL, NPP and cuda-compat are simply not installed.

Why

  • .env holds everything that changes per PC: folders, settings, later passwords. compose.yml stays the same everywhere. Never put .env on GitHub.
  • Windows: if your code opens them (step 1, the Screen branch), switch them off the way your code allows before this run. Without X-Ray nothing catches cv2.imshow, and a container has no screen.
  • run --rm, not up -d: compose.yml has restart: unless-stopped. That suits a camera stream that should run forever. A program that works through one video file and then ends would be started again by up -d every time it finishes.
  • The service is called zip-main after the folder name ZIP-main.

  • Your program prints what it printed in step 6, and its output file is in xout\.
