The driver comes from your PC

It is the only GPU part that does. --gpus all mounts libcuda.so, libnvidia-ml.so and nvidia-smi into the container. Everything else must be in the image.

Wheels bring most of their libraries

opencv-python carries its own FFmpeg and Qt. Only a few libraries are expected from the system. Those, and only those, go into the apt line.

Libraries are found by name

Linux looks in its standard folders plus LD_LIBRARY_PATH. A library outside those folders is "not found", even if it is in the image.

Why

  • pip update: when the Python on your PC is older than 3.12, pip 24.1 and older check package versions against your PC's Python instead of the image's 3.12, and step 2 shows wrong versions. The tool warns about it; updating pip takes a few seconds and avoids it.
  • nvidia-smi in a container proves three things at once: Docker runs, the GPU reaches containers, and your driver is new enough for CUDA 12.8 images. The same command works on any PC with an NVIDIA GPU, a driver 570 or newer, and Docker that can pass the GPU (Windows: Docker Desktop with WSL 2; Linux: the NVIDIA Container Toolkit). Nothing in it is specific to your RTX 3060.
  • That nvidia-smi is not in the image. --gpus all mounts it in from your Windows driver. You will meet this again in step 5.
  • Clean start: results from last time must not mix with today's. "No such image" is fine. Keep any nvidia/cuda image you already have: Docker reuses it and does not download 3 GB again.

Check

  • The nvidia-smi table shows your card. Top right, CUDA Version is 12.8 or higher.
  • unsatisfied condition: cuda>=12.8: update the NVIDIA driver (570 or newer).
  • could not select device driver: Docker Desktop cannot see the GPU. Restart Docker Desktop, then update the driver.

What this step decides

  • GPU. If the System branch lists CUDAExecutionProvider, the code asks onnxruntime for the GPU. Step 2 reads that from this file and builds a GPU image.
  • Files from your PC. Files the code reads from C:\ or D:\ (your model, your video) do not exist in a container. Step 2 decides for each one: copied into the image, or kept outside and mounted, and sets its env var to the path inside the container.
  • Window. If the report lists cv2.imshow: a container has no screen. During the runs X-Ray switches windows off and saves a frame every 5 s instead.
  • Packages. A package listed here but missing from your requirements file: step 6 shows whether the program really loads it.
  • NOT USED: files the program never touches. They stay out of the slim image.

Check

  • CODE CHANGES says none. If it lists something (a hardcoded path, a password), sort that out first.
  • Every file you know is important appears in the tree or is read through an env var.

Choose the base image and the libraries

10–20 min · CMD + Notepad · the heart of the "why"

CMD · tools folder
python xray_naive.py --project "%P%" --requirements requirements.docker.txt --entry live_video.py --name zip --static runs\zip\zip.json
notepad runs\zip\naive\naive-check.txt
notepad runs\zip\naive\Dockerfile.naive

Your model and video are on your PC, not in ZIP-main. The end of naive-check.txt, FILES OUTSIDE THE PROJECT, has three parts:

  • Every env var your code reads: its value in your code (C:\Users\...\Desktop\...\best_blend.onnx) and what it becomes in the container (/xin/model_onnx/best_blend.onnx, set by an ENV line), outputs (/xout/...), and the ones used as they are.
  • CODE CHANGES NEEDED: a Windows path written in the code without os.getenv cannot be changed by any Docker setting. WHERE (file:line), NOW, CHANGE TO; the old value stays the default, so your PC runs as before.
  • Copy or keep outside: a file up to 500 MB that exists on your PC is COPIED into the image (it runs anywhere on its own); bigger ones are KEPT OUTSIDE and mounted with -v. Your choice wins: run the same command again with --copy MODEL_ONNX or --mount MODEL_ONNX (the env var name; or all). Then the exact build and run commands, and how to pass env vars (-e NAME=value, or --env-file).

Lines pip will not install together (the error the worker's build had). A pip freeze comes from a PC where packages were installed at different times, e.g. torch first, newer nvidia-* later; pip only warned there. A Docker build installs the whole file in ONE pip install, and pip refuses the same combination. naive-check.txt then lists those lines as INSTALLED IN A SECOND STEP, exactly this version - pip says: ..., and Dockerfile.naive installs them in section 3c, after everything else, with --no-deps: the same way your PC got them. Nothing is left out, no version is changed; what they need that is not in your file is added right after (ADDED). The build log then shows pip's warning and pip check lines, the same your PC had; the build goes on. Whether the program works with those versions: run-naive (step 4), xray_look.py --image (step 5) and the runs.

Two packages that install the same files, e.g. opencv-python and opencv-python-headless in one file: both write into cv2/, so the one installed last overwrites the other's files. The tool reads each wheel's file list from the package index (a few KB, not the download) and finds such pairs for any packages (PyJWT + jwt, pymongo + bson ...). It keeps one, says which and why under HANDLED, and --keep NAME picks the other. Python version: the check runs for --python (default 3.12). If the project runs on another Python on its PC, pass that one; naive-check.txt warns when the PC running the check has a different Python.

For every line of the requirements, the tool asks pip which file it would download for Linux and Python 3.12. Nothing gets installed. From those answers it writes the Dockerfile. Read naive-check.txt first, then the Dockerfile next to the explanations below.

Dockerfile.naive, section by section

1Base image

Dockerfile.naive
FROM nvidia/cuda:12.8.1-cudnn-runtime-ubuntu24.04
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 \
    DEBIAN_FRONTEND=noninteractive
12.8.1 CUDAcudnn cuDNN 9runtime libraries onlyubuntu24.04 Python 3.12
  • onnxruntime-gpu holds onnxruntime's own GPU code, but not NVIDIA's CUDA libraries. When you ask for the GPU, it opens libcudart, libcublas, libcufft, libcurand, libnvrtc and libcudnn by name. No package in the requirements brings them, so the base image has to.
  • 12.8.1: these CUDA libraries know every current RTX card, RTX 50xx included (12.8 is the first CUDA that knows Blackwell). Needs driver 570+ (step 0 checked that). A framework must also be built for the card: torch +cu126 is not built for RTX 50xx, whatever CUDA the base has; the naive check notes that. Your RTX 3060 works with all of them.
  • cudnn: cuDNN 9 is included; onnxruntime needs libcudnn.so.9.
  • runtime: libraries only. -devel adds the compiler nvcc and headers, about 5 GB more, needed only to compile CUDA code. -base has only libcudart, too little.
  • ubuntu24.04: its Python is 3.12, the version the check ran for.
  • ENV: prints reach the log at once; no .pyc files. ARG DEBIAN_FRONTEND=noninteractive: apt never stops to ask a question while building (no "debconf: unable to initialize frontend" lines); ARG exists only during the build.

2System libraries (apt)

Dockerfile.naive
RUN apt-get update && apt-get install -y --no-install-recommends \
        python3 python3-venv libgl1 libglib2.0-0t64 libx11-6 libxcb1 \
 && rm -rf /var/lib/apt/lists/*
RUN python3 -m venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
  • python3, python3-venv: the CUDA image has no Python. Ubuntu's own python3 has no pip and refuses pip installs into the system Python. A venv brings its own pip; first on PATH, python and pip mean the venv everywhere.
  • libgl1, libglib2.0-0t64, libx11-6, libxcb1: cv2 was built against these and Linux loads them at import cv2. Without libgl1: ImportError: libGL.so.1 (you will cause this on purpose in step 5). t64 is glib's name on Ubuntu 24.04.
  • Cost practice: 254 MB for 53 packages. 137 MB is LLVM, pulled by libgl1 → libglx0 → libglx-mesa0 → mesa-libgallium → libllvm20 (Mesa's software OpenGL).
  • --no-install-recommends: only real dependencies. rm -rf .../lists: the package index is not needed after installing.

3aBig framework first

Dockerfile.naive
RUN pip install --no-cache-dir \
        'onnxruntime-gpu==1.22.0'
  • One layer for the biggest package: 619 MB with its dependencies (numpy, sympy, protobuf). Docker keeps every layer; when a line below changes, this one is reused instead of downloaded again.
  • --no-cache-dir: pip's download cache would otherwise stay in the image.

3bThe other packages

Dockerfile.naive
#   nothing to compile: every package has a prebuilt wheel
RUN pip install --no-cache-dir \
        'numpy' 'opencv-python' 'nvidia-ml-py'
  • All of them have prebuilt Linux wheels, so no compiler is installed (gcc would add about 200 MB).
  • nvidia-ml-py is pure Python. It calls libnvidia-ml.so, which comes with the driver.

3cSecond step (only when needed)

Dockerfile.naive · tested with matplotlib==3.6.1 + seaborn==0.13.2
RUN pip install --no-cache-dir --no-deps \
        'seaborn==0.13.2' \
 && pip freeze > /tmp/xray-installed.txt \
 && (pip install --no-cache-dir -c /tmp/xray-installed.txt \
        'pandas>=1.2' \
     || echo "...") \
 && (pip check || true)
  • ZIP's file has no such lines, so its Dockerfile has no 3c. The example is a test file in which seaborn 0.13.2 rejects matplotlib 3.6.1.
  • --no-deps: installed exactly as pinned, without pip changing the versions installed above.
  • -c (the versions installed so far): what seaborn needs that is not in the file (pandas) is added without moving any of them.
  • pip check || true: prints the mismatch in the build log; the build goes on. In the test the image built and the program ran with every version as pinned.

4LD_LIBRARY_PATH: nothing to add

  • The base image already sets LD_LIBRARY_PATH=/usr/local/cuda/lib64 and keeps cuDNN in /usr/lib/x86_64-linux-gnu, a folder Linux always searches. Step 10 is the case where this line is needed.

  • Dockerfile.naive.dockerignore keeps .git, venvs and caches out even here.
  • Section 6: the files the code reads from your PC. Why

  • Files the code reads from your PC that are not copied into the image (step 2): -v mounts their folders into the container, read-only. A file that is in the image needs no mount; the env var points at it either way.
  • Inside the container the paths are different, so the env vars point at the container paths: /xin for inputs, /xout for outputs (kept in runs\zip\out).
  • run.env holds every env var once; all run files read it.

How long it runs, loop, several videos: the top of every run file

the top of run-slim.bat, as xray_runfile writes it · change the set lines in Notepad, save
REM ---- settings: change them here, then run this file ----
REM RUN_SECONDS: how long the program runs, then it is stopped (0 = until it ends by itself or you stop it)
set "RUN_SECONDS=180"
REM LOOP: 1 = a video FILE starts again from the beginning when it ends (the program keeps working)
set "LOOP=0"
REM VIDEOS: a folder with videos (.mp4 .avi .mov ...): the program plays them one after the other instead
REM         of its own video (with LOOP=1 the list starts again). Empty = the program's own video.
REM         (both only matter for programs that read video FILES; cameras / streams are not touched)
set "VIDEOS="

A folder name with spaces is fine: set "VIDEOS=D:\test videos" (the quotes go around the whole VIDEOS=..., as in the line above).

You wantSet
the slim image for 10 minutes on a 2-minute videorun-slim.bat: RUN_SECONDS=600, LOOP=1
three different videos, one after the other, onceput them in one folder; VIDEOS=that folder, LOOP=0, RUN_SECONDS=0
the same three for an hourVIDEOS=that folder, LOOP=1, RUN_SECONDS=3600

Practice: a folder with a 300-frame and a 100-frame video, LOOP=0: the program read 400 frames and ended by itself. LOOP=1, RUN_SECONDS=15: it kept reading and was stopped after 15.1 s. Only video FILES opened with cv2.VideoCapture change; cameras and rtsp:// streams never. A program that writes its results only at its end writes nothing when RUN_SECONDS stops it first. Defaults: run-step2 / run-slim 180 s, run-load 300 s, run-explore 0 (until you stop it), run-naive 120 s (no X-Ray there, so no LOOP / VIDEOS).

A is bigger because its base image also brings CUDA parts this program never loads (cuSOLVER, cuSPARSE, NCCL, NPP: about 2 GB, "NOT used in the run"). For a project with torch it can go the other way: torch's pip wheels already bring CUDA, so an nvidia/cuda base under it is a second copy. The comparison shows which case you have, with sizes.

Why

  • .env holds everything that changes per PC: folders, settings, later passwords. compose.yml stays the same everywhere. Never put .env on GitHub.
  • Windows: if your code opens them (step 1, the Screen branch), switch them off the way your code allows before this run. Without X-Ray nothing catches cv2.imshow, and a container has no screen.
  • run --rm, not up -d: compose.yml has restart: unless-stopped. That suits a camera stream that should run forever. A program that works through one video file and then ends would be started again by up -d every time it finishes.
  • The service is called zip-main after the folder name ZIP-main.

Check

  • Your program prints what it printed in step 6, and its output file is in xout\.
